# Task w4-create-dev-user — CLI script to create developer admin users

## Goal
A command-line script, run by hand on a machine that already has database access (local, test server, production server), that creates a real `AdminUser` row for a developer with ALL permissions. It is a provisioning tool, not a login bypass: the account still signs in through the normal login (password, and the email code if enabled).

## Read first
`server/prisma/seed.ts` (the `ADMIN_USERS` entries, `seedAdminUsers`, the `role_super_admin` role at ~line 179, how `roleId`, `roleAr`, `permissions` JSON are stored, how it avoids loading `src/config/env`), `server/prisma/schema.prisma` (`AdminUser`, `Role`), `server/src/config/permissions.ts` (`PERMISSION_KEYS`, `parsePermissions`), `server/src/services/passwordPolicy.ts` (`meetsPasswordPolicy`), `server/src/routes/auth.routes.ts` (how `super_admin` is treated, bcrypt cost 10, lockout/login failure handling in `server/src/services/loginFailureService.ts`), `server/package.json`, root `package.json`, `server/scripts/migrate-developer-notes.ts` (an existing tsx script: follow its style and env handling), `deploy/README-deploy.md` (§3.3 mentions the seed password rules).

## Decided design
- File `server/scripts/create-dev-user.ts`, run with tsx from `server/`. Scripts: `server/package.json` gets `"user:create-dev": "tsx scripts/create-dev-user.ts"`; the root `package.json` gets `"user:create-dev": "npm --prefix server run user:create-dev --"` so `npm run user:create-dev -- --email dev@example.com --name "Dev Name"` works from the root.
- Arguments: `--email <email>` (required, trimmed, lowercased, validated), `--name <full name>` (required, 2-80 chars), `--phone <number>` (optional), `--generate` (generate the password instead of prompting), `--reset-password` (see below), `--yes` (skip the confirmation prompt, only allowed when the database name ends with `_test` or the database is local; never for any other database).
- The new user: `role = 'super_admin'`, `roleId = 'role_super_admin'`, `roleAr` and department exactly as the seeded super admin entry uses, `status = 'active'`, `permissions` = JSON object with EVERY key in `PERMISSION_KEYS` set to `true` (explicit, not relying on the implicit super_admin rule), `passwordChangedAt = now`. Ensure the `role_super_admin` role row exists (read it; if it does not, abort with a clear message telling the owner to run the migrations/seed; do not create roles here).
- Password: NEVER accepted as a command-line argument or environment variable (shell history and process lists leak both). Default: prompt twice on the TTY with hidden input (implement hidden input with `readline` + muted output or `process.stdin.setRawMode`; no new dependency); must pass `meetsPasswordPolicy`. With `--generate`: create a 20-character random password with `crypto.randomInt` (letters + digits, at least one of each), print it ONCE to the terminal at the end with a line telling the owner to change it at first login, and never write it to any file or log. Hash with `bcryptjs` cost 10 like the app.
- Existing email: abort with "user already exists" and exit code 1 (never modify an existing user by default). With `--reset-password`: only for an existing user, set a new password (same prompt/generate rules), set `passwordChangedAt = now`, clear any login lockout state for that email using the same mechanism `loginFailureService` uses, and leave role, permissions and everything else untouched.
- Safety: before any write, print the database NAME only (parsed from `DATABASE_URL`, never the URL, host, user or password), the email, the name and the role, and ask for confirmation by typing the database name (typing `yes` is not enough). If the database name does not end with `_test` (that is, production), additionally require `NODE_ENV=production` to be explicitly acknowledged by the typed name; there is no `--yes` for it. Exit code 0 on success, 1 on any refusal or error; errors never print secrets.
- Env: follow what `seed.ts` / `migrate-developer-notes.ts` do to get `DATABASE_URL` (Prisma loads `server/.env` when run from `server/`); do not import `src/config/env` if it exits the process on missing production secrets (the seed has the same constraint; see its comment).
- After creating, print: the login URL hint ("sign in at /admin/login"), whether email-code login is enabled for the account (read `loginOtpEnabled`), and a reminder that the user should enable their authenticator/second factor when that feature exists. Do not print the password except with `--generate`.
- Tests (vitest, `server/test/`): extract the pure parts into `server/scripts/lib/devUser.ts` (argument parsing, email normalisation/validation, `buildDevUserData(email, name, phone, passwordHash)` returning the Prisma create payload incl. all-permission JSON, password generator) and unit-test them: every permission key is true, generated passwords always satisfy `meetsPasswordPolicy`, bad emails and short names are rejected, passwords given on the command line are rejected with a clear error (`--password` must be an unknown/forbidden flag). The DB path is not unit-tested; verify it manually against the local database.
- Docs: add a short section "Create a developer user" to `deploy/README-deploy.md` (right after §3.4.1) with the exact commands for test and production (`cd /srv/ajda/test && npm run user:create-dev -- --email ... --name "..."` and the `--generate` and `--reset-password` variants), noting that production use is by hand by the owner only, never from CI.

## Out of scope
The admin UI, auth routes, seed file, any schema change or migration, 2FA/email-verification features (separate auth lane), any bypass or "dev email" login path, any CI change.

## Constraints
No commits, no installs, no new dependencies, do not touch `.env*`. keep each file's existing line endings (the tree is CRLF with no `.gitattributes`; never rewrite a whole file just to change them). Match surrounding style and comment density. Never log or print password hashes or the `DATABASE_URL`.

## Gates
`npm --prefix server run build`, `npm --prefix server run test` (all pass; the flaky pre-existing mail-settings "tampered box" test may fail alone: re-run once and say so), `npm run lint`. Manual run against the LOCAL development database only (never test or production): create a user with the prompt, create another with `--generate`, run again for the same email (must refuse), run `--reset-password` on it, try `--password x` (must be refused), try a wrong confirmation (must abort without writing). Then sign in to the admin with the generated account in the browser (`npx vite --port 5193 --strictPort`, API on 4000; port 5191 belongs to the owner's auth dev server) and confirm every sidebar section is visible. Delete the accounts you created from the local database afterwards and list in the report that you did.
