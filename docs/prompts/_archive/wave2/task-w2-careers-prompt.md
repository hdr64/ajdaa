## Verified facts
- `JobApplication`: `id` cuid, `name`, `email`, `phone`, `jobTitle` (all required, NOT NULL), `message?`, `cvPath?` (relative path of a PRIVATE file), `cvOriginalName?`, `status` default `new` (`new|reviewed|shortlisted|rejected|hired`, constants + Arabic labels in `config/constants.ts`), `adminNote?`, `createdAt`, `updatedAt`, indexes on `status` and `createdAt`.
- Permissions `viewApplications` (list, view, download CV) and `manageApplications` (status, note, delete, settings) exist. Notification event `job_application` exists with its own per-event configured state (`emailRecipientsFor('job_application')` returns `null` until a listener for it exists). `careersSettings.ts` has `getCareersFormConfig()`/`setCareersFormConfig()`; name/email/phone are forced required.
- Everything under `UPLOAD_DIR` is served publicly at `/uploads/` without authentication: CVs must NEVER be stored there.
- `listenersConfigured`/`emailRecipientsFor` fallback semantics must stay as they are.

## Decided design
**A. Config and private storage**
1. `jobTitle` becomes always-required: add it to `ALWAYS_REQUIRED_FIELDS` in `careersSettings.ts` (getter and setter force it) and update `careersSettings.test.ts` accordingly.
2. New env `PRIVATE_DIR` (default `./private`, resolved like `uploadDir`; `config.privateDir`), documented in `server/.env.example`. Never served by `fastifyStatic`. CVs are stored in `<PRIVATE_DIR>/cv/` under a random server-generated name `<24 random hex>.pdf` (never the client name; the original client name is kept only in `cvOriginalName`, sanitised: strip path separators and control characters, max 120 chars). `cvPath` stores `cv/<name>.pdf` (relative). Add `private/` to `.gitignore` if not present. `server/test/env.ts` must point `PRIVATE_DIR` at the per-run temp directory and the global teardown must remove it.
3. CV rules: `application/pdf` only AND the file starts with `%PDF-`; max 5 MB; one file. Reject with 400 and a clear message otherwise. Write the file only after the application row validation has passed; if the DB insert fails, delete the written file.

**B. Public API** (new `server/src/routes/careers.routes.ts`, registered in `server/src/app.ts` with prefix `/api/careers`: one import and one `register` line; also `registerJob(...)` for your new job next to the existing ones):
4. `GET /api/careers/form` public: `{ required: {name,email,phone,jobTitle,message,cv} }` from `getCareersFormConfig()`.
5. `POST /api/careers/applications` public, `multipart/form-data` (fields `name,email,phone,jobTitle,message`, file `cv`, honeypot field `website`), per-IP rate limit 5 per 10 minutes via the route `config.rateLimit`. Server-side validation driven by the stored config: required flags enforced, `name` ≤ 120, `email` valid ≤ 200, `phone` 7-20 chars of digits/space/+/-/(), `jobTitle` ≤ 150, `message` ≤ 3000. If the honeypot is non-empty answer 201 with the same body as success but store nothing. Respond `201 { ok: true }` (never echo stored data or the id). On success dispatch the notification job (see D).
6. Never log names, emails, phones, messages or CV names (log only the application id and status).

**C. Admin API** (guards `authenticate` + `requirePermission`):
7. `GET /api/careers/applications` (`viewApplications`): query `status` (optional, one of the constants), `q` (optional, matches name/email/phone/jobTitle, contains, case-insensitive), `page` (default 1) and `limit` (default 20, max 100); response `{ items, total, page, limit }`, newest first; list items do not include `message` or `adminNote` bodies (only a `hasCv` boolean).
8. `GET /api/careers/applications/:id` (`viewApplications`): full record without `cvPath`; adds `hasCv`.
9. `GET /api/careers/applications/:id/cv` (`viewApplications`): streams the PDF from the private directory with `Content-Type: application/pdf`, `Content-Disposition: attachment; filename*=UTF-8''<encoded sanitised original name>`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`. Path safety: resolve `<PRIVATE_DIR>/<cvPath>`, require the result to stay inside `<PRIVATE_DIR>/cv/`, 404 if the row or the file is missing.
10. `PATCH /api/careers/applications/:id` (`manageApplications`): body `{ status?, adminNote? }` (status from the constants, note ≤ 2000).
11. `DELETE /api/careers/applications/:id` (`manageApplications`): deletes the row and its CV file (ignore a missing file).
12. `GET /api/careers/settings` and `PUT /api/careers/settings` (`manageApplications`): `{ required: {...partial}, notificationEmails: string[] }`. `required` uses `setCareersFormConfig`. `notificationEmails` is stored in an `AppSetting` row `careers.notifications` as `{ "emails": [...] }` (max 10 valid, lower-cased, de-duplicated emails), with a small typed helper in `server/src/services/careersSettings.ts` (get/set, with the same lenient-read/strict-write behaviour).

**D. Notifications**
13. Add `toApplicationViewers: boolean` to `EmailListenerConfig` (default false, parsed leniently for old rows, accepted by the listener route schema, stored by `normaliseConfig`) and `activeApplicationViewerEmails()` (active admins holding `viewApplications`; super admin counts). `emailRecipientsFor(event)` resolves `toApplicationViewers` for listeners and `toInquiryViewers` as before (each flag only meaningful for its own event; a `job_application` listener with `toInquiryViewers` set must NOT mail inquiry viewers: ignore that flag for that event).
14. New queue job `email:job-application` (file `server/src/jobs/emailJobs.ts`, registered in `app.ts`): recipients = `emailRecipientsFor('job_application')` when not null, otherwise `careers.notifications` emails if any, otherwise `activeApplicationViewerEmails()`. Template in `mailTemplates.ts` (Arabic first, like the existing ones): applicant name, job title, time, and a button linking to the admin applications page; NO phone, email, message or CV in the mail body, no attachment. A mail failure must propagate (the queue retries) and must not fail the applicant's request (dispatch is fire-and-forget as for inquiries).

**E. Frontend**
15. Public: page `CareersPage` at `/careers` (page key `careers`): register in `App.tsx` (`parsePath`, `getPathForRoute`, lazy render). Footer: add a link "قدّم على وظيفة" / "Apply for a job" in `Footer.tsx` navigating to it (existing navigate helper). Form: fields from `GET /api/careers/form` (required marks and client validation mirror the server rules), CV file input accepting PDF only with client-side size/type check, hidden honeypot field (visually hidden, `tabIndex=-1`, `autoComplete="off"`), submit button disabled while sending, success state, error messages from the server shown under fields, Arabic first with English via the existing language hook. Do not add careers to the CMS nav default items (the footer link is the entry point).
16. Admin: new section `applications` (route `/admin/applications`), registered in `adminRoutes.ts`, `AdminSidebar.tsx` (label "طلبات التوظيف", visible with `viewApplications` or super admin) and `AdminDashboardPage.tsx`. New files `src/pages/admin/sections/ApplicationsSection.tsx`, `src/components/admin/applications/*`, `src/services/careersService.ts`. UI: list with status filter, search, pagination, status badge (Arabic labels), new count; detail drawer/panel with all fields, status select, admin note, delete with confirm (both gated by `manageApplications`), CV download button that fetches with the auth header and saves the blob (never an `<a href>` to a URL without auth); a "الإعدادات" tab (gated by `manageApplications`) with checkboxes for the optional required flags (name/email/phone/jobTitle shown checked and disabled) and an editable list of notification emails. Loading, empty and error states.
17. The new `toApplicationViewers` option must be selectable in the notification listeners panel for the `job_application` event (`src/components/admin/settings/NotificationListenersPanel.tsx` + `src/services/notificationsService.ts`: add the event label from the server labels or the UI map, and the checkbox "المستخدمون الذين لديهم صلاحية طلبات التوظيف"); keep inquiry behaviour identical.
